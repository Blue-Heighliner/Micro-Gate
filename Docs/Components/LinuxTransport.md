# Linux transport

Covers `LibC`, `LinuxNative`, `LinuxMicroGateDevice`, `SynclinkParams`, `SynclinkConstants`, and `LinuxMicroGatePorts` (all internal, namespace `BlueHeighliner.MicroGate.Linux`). The SyncLink kernel driver exposes a tty device driven through `open`, `read`, `write`, `ioctl`, and `fcntl` from libc; there is no DLL and no link-layer engine.

## P/Invoke surface

`LibC` declares only the calls needed, with PascalCase managed names bound to the libc symbols through `EntryPoint`. `fcntl` has get and set overloads, and `ioctl` has three overloads (`ref int`, `ref SynclinkParams`, and a plain `nint`) matching how the driver interprets each request's argument; the request code itself is a `nuint`, because the C declaration takes an `unsigned long` and passing a 32-bit value would leave the upper half of the register unspecified. `LinuxNative` (behind `ILinuxNative`) turns those into semantic operations such as `EnableReceiver` and `SetParams`, choosing the request code and argument shape, and retries `read`, `write`, and `tcdrain` when a signal interrupts them (`EINTR`), reporting an interrupted `poll` as a timeout; without that, any signal delivered to the receive thread would look like a device failure and end the link, and `LinuxMicroGateDevice` builds the frame transport on it: a write that is not fully accepted throws `IOException`, and each successful write is followed by `tcdrain` so the frame has left the device.

## Native struct layout

`SynclinkParams` mirrors `struct _MGSL_PARAMS` from `synclink.h` as laid out on 64-bit Linux, where `unsigned long` is 8 bytes (`nuint`) rather than the 4 bytes of the Windows `ULONG`. This is the one place the two platforms' native structs differ in shape and not just name.

## Request codes

`SynclinkConstants` holds the HDLC mode, the disabled address filter, and the enable values (numerically identical to the Windows header's, since both SDKs share a driver lineage), the `N_HDLC` line discipline number, and the `open`, `fcntl`, and `poll` flag values. Encoding, CRC, and idle pattern values come straight from the public option enums, whose values match both headers. The `MGSL_IOC*` request codes are computed at class initialization by replicating the kernel's `_IO` and `_IOW` macros, with `Marshal.SizeOf<SynclinkParams>()` feeding the size field, so they cannot drift from the marshaled struct size. Values are `static readonly` rather than `const` so they are never baked into other assemblies.

## Port configuration

A port name that is not a rooted path is resolved under `/dev`, so `ttySLG0` and `/dev/ttySLG0` are equivalent.

Opening uses `O_NONBLOCK` only so the open does not wait on DCD, and `O_NOCTTY` so the tty never becomes the process's controlling terminal; the flag is cleared afterwards so reads and writes block, matching the vendor's Linux sample. The sequence is: select the `N_HDLC` line discipline (`TIOCSETD`), which makes each read return exactly one frame and each write send one, apply `MGSL_IOCSPARAMS`, set the idle pattern from the options, enable receiver and transmitter, then clear `O_NONBLOCK`. Every step is checked: a negative result throws `IOException` naming the step and the device, because a tty that rejects these calls is not a SyncLink device (or lacks the `N_HDLC` line discipline) and would otherwise never produce frames.

After the HDLC line discipline is selected, the serial interface is set to RS-232 (`MGSL_IOCSIF`) on a best-effort basis: the result is ignored, since changing it can need privileges the user lacks and a device that cannot switch is still usable as it is. The parameters are then: HDLC mode; the encoding, CRC, clocking, preamble, and underrun settings from `MicroGatePeerOptions`, each enum member mapped explicitly to the driver's numeric constant, with the clocking, underrun action, and phase locked loop divisor packed into the parameters' `Flags`; the idle pattern, set separately; and a hardware address filter that is always disabled (`0xFF`), because address filtering happens in `HdlcStateMachine`. The monitor's opener sets the same interface and the encoding, CRC, and an optional address filter, and never enables the transmitter. Frames failing the CRC are discarded by the driver and never reach `read`, and so are received frames over 4096 bytes, which is where the peer's payload limit comes from. The driver documentation does not promise that disabling the receiver (`MGSL_IOCRXENABLE` with 0) wakes a blocked read, so `LinuxMicroGateDevice` does not depend on it: a read is a loop of `poll` calls with a short timeout followed by one `read` once the descriptor is readable, checking a flag between polls, so disposal ends the receive loop within one poll interval whatever the driver does. Disabling the transmitter (`MGSL_IOCTXENABLE` with 0) is what disposal uses to cancel a `write` or `tcdrain` that blocks because the cable is unplugged or no clock is present.

## Port enumeration

`LinuxMicroGatePorts` (whose device and alias folders are constructor parameters, defaulting to `/dev` and `/dev/serial/by-id`) lists `/dev/ttySLG*`, the PCI and PCIe adapters, which are always MicroGate. USB adapters appear as `/dev/ttyUSBx`, a name shared with every other USB serial device, so they are recognized by the udev alias the driver documentation describes: an entry named `usb-MicroGate_...` in `/dev/serial/by-id`, whose link target is the device. The alias is resolved to the target's file name, aliases whose device no longer exists are skipped, and several aliases for one device collapse to one port. This depends on udev creating the aliases, which it does by default; without them, USB adapters can still be used by passing the device name directly. Names are returned sorted ordinally.
