# Peer lifecycle

Covers `MicroGatePeer`, `IMicroGateDevice` and its two implementations (`LinuxMicroGateDevice`, `WindowsMicroGateDevice`), the device openers (`IMicroGateDeviceOpener`, `LinuxMicroGateDeviceOpener`, `WindowsMicroGateDeviceOpener`; all internal), plus how `MicroGatePeer` and `MicroGatePortSource` dispatch to them.

## Device abstraction

`IMicroGateDevice` is the raw, frame-oriented transport of an opened and configured device: a blocking `Read` of one frame, a `Write` of one frame, `DisableReceiver` to cancel a blocked read (and make later reads return at once), and `DisableTransmitter` to cancel a blocked write; disposing closes the device. It is the only thing that differs between platforms. `MicroGatePeer` is the single `IMicroGatePeer` implementation for both, so the receive loop, sending, and disposal behave identically everywhere and can be exercised with a mock or an in-memory device.

Each platform device is a thin wrapper over a native interface (`ILinuxNative`, `IWindowsNative`) that hides pointers, `ref` parameters, and request codes behind semantic operations. The interface implementations (`LinuxNative`, `WindowsNative`) are the only code that calls into the P/Invoke declarations, so everything above them is testable without hardware or the native library.

## Starting

The public constructor wires in the two platform `IMicroGateDeviceOpener`s; nothing is opened and there is no state machine yet. `Start(portName, options)` first validates the options (an interval that is zero, negative, or beyond what timers accept, or a non-positive `MaxRetransmissions`, throws `ArgumentOutOfRangeException`) and selects the opener for the running operating system (`PlatformNotSupportedException` otherwise); both leave the peer `Idle`. It then claims the peer by moving `Idle` to `Connecting` under the state lock (a second start throws `InvalidOperationException`), creates a fresh `HdlcStateMachine` from the options, opens the device through the opener on the thread pool, starts the receive loop, and then establishes the link. Establishing sends a SABM request when `RetryInterval` is set and waits for a `TaskCompletionSource` that the receive loop completes when the state machine first reports `Connected` (the remote peer's UA, or an inbound SABM). If the wait times out at the retry interval the request is sent again, so requests repeat until the link is up; with a `null` interval the wait has no timeout and nothing is sent. The opener applies the physical layer configuration, checking the result of every native call, and if any fails it disposes the device and throws `IOException` naming the step and the device, so a tty that is not a SyncLink device fails at start rather than by silently never connecting. Because the state machine only exists once started, `Send` before then throws `InvalidOperationException`.

Any failure while starting, including cancellation, disposes the peer and rethrows, so a failed start never leaks a handle and always leaves the peer `Disconnected`. Cancellation is checked after the device opens rather than passed to the open, so a device opened concurrently with a cancel is still disposed. If the receive loop ends before the link is established, the start fails with `IOException`, unless the reason is that the peer was disposed meanwhile, in which case it fails with `ObjectDisposedException` so the caller can tell the two apart. Each request is created only if the state machine is not already connected, which prevents a retry from knocking a link that a remote request just brought up back to `Connecting`.

## Protocol lock and sending window

The state machine is not thread safe and is touched by the receive loop, `Send` calls, retried requests, retransmissions, and disposal, so every call into it goes through one short protocol lock that never covers I/O. The retransmission bookkeeping (when the oldest unacknowledged frame was sent, and how many resends have passed) lives under the same lock, so an acknowledgement and a concurrent send cannot overwrite each other's update.

Wire order is kept by the write lock, which covers building a frame and writing it. Every writer takes it: sends, retried requests, timer resends, disposal's DISC, and the receive loop, which holds it for the whole of processing an inbound frame (updating the state machine, writing the response, and writing any frames a rejection or reset asks for). So no frame can be built from one state machine state and written after an inbound frame has changed that state, which matters for a link reset: a send that built its frame just before a reset would otherwise put a frame with an old sequence number on the wire after the reset. Resent frames are built at the moment they are written, so they carry current sequence numbers. Lock order is write lock, then protocol lock. A write that blocks holds the write lock, so it also holds up the receive loop; that is no worse than before, since the loop has to write its acknowledgement anyway, and disposal breaks it by disabling the transmitter.

The 7-frame send window is a semaphore sized from the state machine. `Send` takes a slot before creating its frame, the receive loop returns slots as acknowledgements arrive (the state machine reports how many frames each received frame acknowledged, including frames discarded by a sequence reset), and a slot is returned immediately if the frame was never created. A send that has to wait links its token with the peer's lifetime token, so disconnecting fails it with `IOException` instead of leaving it waiting forever.

## Retransmission

The state machine keeps a copy of every unacknowledged payload. A REJ from the remote peer acknowledges the frames before it and flags a resend, which the receive loop performs immediately. A retransmit task ticks at half the `RetransmitInterval` (at least one millisecond, the finest period the timer accepts); the peer records when the oldest unacknowledged frame was sent (restarted whenever an acknowledgement arrives while frames remain) and, once that is older than the interval, sends all outstanding frames again and counts an attempt. The count returns to zero whenever anything is acknowledged. When it exceeds `MaxRetransmissions` the peer fails: the pending start and waiting sends fail, the state becomes `Disconnected` and both streams complete, and the receiver is disabled so the loop ends; the device stays open until disposal, like every other failure. The same failure path handles an unexpected exception in the task, so it can never stop silently. Nothing runs when the interval is `null`. The task stops with the peer's lifetime token, and disposal waits for it before closing the device.

A send whose device write fails is rolled back inside the write lock: the state machine forgets the newest frame and gives its sequence number back, and the window slot is returned, so a caller retry is not a duplicate.

## State and observables

Peer state moves strictly forward. Everything observers see goes through one notification queue: a state transition is applied under the state lock and its notification queued there, a received payload is copied and queued by the receive loop, and reaching `Disconnected` queues the completion of both streams after the final state, exactly once (nothing more is queued after it). Whichever thread finds no notification running drains the queue after releasing the lock, recording its thread identity while it does. So observers never run inside a peer lock, see everything in order, and are never called concurrently, including when completion is caused by the retransmission task or by disposal while the receive loop is still delivering data. A callback that re-enters the peer only enqueues, and its notification is delivered when the running one returns. The draining thread is usually the receive loop; if another thread is already draining, the loop queues its payloads and carries on.

The two streams are System.Reactive `Subject<T>`s. Each is exposed through a small wrapper that subscribes the caller's observer with guarded callbacks: an exception thrown by `OnNext` or `OnCompleted` is swallowed, and because Rx unsubscribes an observer whose `OnNext` throws, that observer simply stops receiving, so it can neither break the receive loop nor starve the observers registered after it. A received payload is copied to a new array only when the subject has observers, so an unobserved peer allocates nothing per frame.

## Receive loop

One `Task.Run` thread reads one raw frame at a time into a 65535-byte buffer. Each frame is processed under the write lock: the state machine consumes it, and any response frame and any frames a rejection or reset asks for are written straight away. Frames the parser rejects are dropped. Outside the lock the loop then returns acknowledged send slots, queues a delivered payload (copied out of the reused buffer), marks the peer `Connected` when the state machine is connected, and delivers queued notifications. The loop ends when a read returns zero or less, which disposal and failures trigger by disabling the receiver, when a peer that had been connected is disconnected by the remote side, or when anything in the loop throws (a failed response write, a failing read). However it ends, it fails a pending start (with the exception as the inner exception of an `IOException`) and finishes the peer, so a dead device always surfaces as `Disconnected` and completed streams, never as a silently stalled peer. The device stays open until the peer is disposed.

## Sending

`Send` first checks the payload against `MaxPayloadSize` and that the peer is connected (so a peer that failed, or whose remote peer disconnected, rejects sends), then waits for a window slot, then builds an I-frame with `CreateInformation` and writes it under the write lock. A failed write throws `IOException` and is rolled back as described above, so the frame is neither kept nor resent. Sending while the state machine is not connected throws `InvalidOperationException`. The `IMemoryOwner<byte>` overload disposes its argument after the send, whether or not it succeeds.

## Disposal

`DisposeAsync` is idempotent and safe before starting. If connected it sends DISC, but waits for the write only up to the shutdown timeout (five seconds): a write can block indefinitely when the cable is unplugged or no clock is present, so on timeout the transmitter is disabled, which cancels the blocked write. It then cancels the peer's lifetime (waking waiting senders and stopping the retransmit task), disables the receiver to end the loop, waits for the loop and the retransmit task (again bounded by the timeout, so a driver that never returns from a read cannot hang disposal), disposes the device, and finishes the peer. Synchronous `Dispose` blocks on `DisposeAsync`.

Observer callbacks run on whichever thread is draining notifications, which can be the receive loop or the retransmit task, and waiting for that task from inside the callback would stall until the timeout. Disposal therefore checks whether the current thread is the one draining notifications; if so it sends DISC and disables the receiver as usual but does not wait, and instead a background task waits for the loop and the retransmit task to stop (which they do once the callback returns) and then closes the device. The disconnect state and completion are queued as usual and delivered when the callback returns.

`Start` and disposal can race. Whichever comes second wins cleanly: if disposal happens while the device is opening, `Start` notices under the state lock when the open returns, disposes the just-opened device itself, and fails with `ObjectDisposedException`; if disposal happens after, the device and loop are already registered under that same lock, disposal closes them, and `Start` also fails with `ObjectDisposedException`.

## Platform dispatch

`MicroGatePeer` (which defaults a null options argument to `new MicroGatePeerOptions()`) and `MicroGatePortSource` pick the Windows or Linux implementation with `OperatingSystem.IsWindows()` and `IsLinux()` and throw `PlatformNotSupportedException` elsewhere. Their internal constructors take the platform implementations, which is how dispatch is tested.
