# API

The public API is `IMicroGatePortSource` (discovery), `IHdlcPeer` (one end of a link) with `IHdlcPeerFactory` to create them, plus the `HdlcPeerOptions` record that configures it. A peer also covers passive monitoring and frame relaying (see Monitoring). This document covers the *design and flow* of that surface (how the pieces fit together and the order things happen in) using public types only. It does not restate member-level detail already covered in the source itself.

## Shape

A caller constructs `MicroGatePortSource` and `HdlcPeer` (both with no arguments), or resolves them through a container by their `IThing` to `Thing` naming. Because a peer is single use, code that needs a new link on demand, in particular a service built by a container, depends on `IHdlcPeerFactory` and calls `Create` instead of holding a peer; the factory holds no state and is safe to register as a singleton. Constructing a peer touches no hardware and needs no port: the port name and options are supplied later, to `Start`, which is the first point the device is opened. Constructing and starting are separate so a caller can subscribe to everything the peer emits before any traffic or state change can occur; with a single call that returns an open connection, the first frames and the earliest state changes could be missed.

The concerns are deliberately separate types rather than one facade: discovery is stateless and needs no configuration, and the peer is a stateful, disposable resource with its own lifetime and event streams. Neither exposes HDLC framing or operating system details; a caller sees only port names and payload bytes.

Configuration is passed to `Start` (which opens the device) as an optional `HdlcPeerOptions`, not to the constructor, so a peer needs no configuration to be created, registered in a container, or observed, and the settings arrive together with the port they apply to. The settings are split by whether they must match the remote station, including one that does not use this library (any ADCCP or HDLC station in asynchronous balanced mode): those that must live in a `HdlcLinkOptions` record, exposed as `HdlcPeerOptions.Link`, and everything else sits directly on `HdlcPeerOptions`. Every setting has a default, so omitting the options, or setting only one property, is always valid.

Settings in `Link`, which must match the remote station, or the link fails or frames are garbled or discarded: `Encoding`, `Crc` and the clocking (`ReceiveClockSource`, `TransmitClockSource`, `PhaseLockedLoopDivisor`, `ClockSpeed`). The two addresses that must also match are not options but required arguments of `Connect`, since a link always needs two different ones: `address` is this station's, put in every response and expected in every command, and `remoteAddress` is the remote station's, put in every command and expected in every response. `Connect` throws `ArgumentException` if they are equal. A peer always leaves the driver's own hardware address filter disabled and relies solely on these checks. Address `0xFF` is the all-stations address: connection requests are always sent to it, and a connection request or disconnect addressed to it is accepted like one addressed to this station (no other frame to it is acted on).

Settings on `HdlcPeerOptions` that the remote station can see on the wire but that need not match, provided it tolerates them: `IdlePattern`, `PreambleLength`, `PreamblePattern`, `UnderrunAction` (seen only when an underrun aborts a frame), `DisablePollFinalBit` (which forces the poll/final bit to 0, and so cannot be used with a remote station that polls and waits for a final response), `MaxInfoField` (which caps the payload `Send` accepts, as `MaxPayloadSize` and as an `ArgumentOutOfRangeException` for anything larger, and must not exceed what the remote station can receive; the SyncLink USB devices tested delivered at most 3176 bytes and silently lost larger frames, well below the 4090 the option allows), `RetryInterval` (how often the connection request is re-sent, or `null` to never send one; the remote station sees each request, and one arriving while it is connected resets its link), and `AcknowledgeDelay` (how long a received frame waits for data of this station's own to carry its acknowledgement before a separate RR is sent; zero acknowledges at once; a remote station that polls or times out sooner than this sees its data unacknowledged for that long), `RetransmitInterval` (how long sent data may go unacknowledged before the remote peer is polled for what it has received and anything it lacks is sent again, or `null` to resend only when the remote peer rejects; too short a value sends duplicates; it counts from the end of a frame's transmission, so it does not need to allow for a slow line).

Settings on `HdlcPeerOptions` that only this station can observe and are always safe to change: `MaxRetransmissions` (how many resends without any acknowledgement are tolerated before the remote peer is considered gone, or `null` for no limit), `TransmitWindow` (1 to 7, the most information frames that may be outstanding at once), and `Loopback`.

Most defaults are what the SyncLink drivers themselves default an unconfigured port to (NRZ, flag idle, loopback off, own-pin clocking, divide-by-32 phase locked loop, abort-7 underrun, 4800 bps clock speed, 8-bit preamble, no preamble pattern); the rest are CRC-32-CCITT, requests and retransmissions every second, a 200 millisecond acknowledge delay, 21 retransmissions, poll/final enabled, and a 1500-byte info field. The library speaks standard HDLC and ADCCP asynchronous balanced mode, so it interoperates with any station that does, provided the settings that must match and the two addresses agree. `TransmitWindow` defaults to the maximum of 7, since the window is a purely local sending policy HDLC never negotiates between stations. The enums are plain, sequentially valued, and have no assumed correspondence to the drivers' own bit values; each opener maps every member to its native constant explicitly. The async-mode fields the native struct also carries (data rate, data bits, stop bits, parity) are not part of `HdlcPeerOptions`; they belong to the separate UART peer (see UART peer).

## Flow

1. `IMicroGatePortSource.GetPorts` returns the names of the MicroGate ports on the machine.
2. The caller creates an idle peer with `new HdlcPeer()`.
3. The caller sets the peer's `Receiver` delegate and subscribes to `StateChanged`, `Exceptions`, and, to watch frames, `Monitored`.
4. The caller starts the peer, exactly once, with `Start(portName, options)`. It opens and configures the device for HDLC and completes once the device is open, leaving the peer `Ready`: it reads frames (publishing them on `Monitored` when `EnableMonitor` is set) but forms no connection and, since the transmitter stays disabled, sends nothing. Invalid options (an interval that is zero, negative, or longer than `int.MaxValue` milliseconds, a `MaxRetransmissions` of zero or less, a `TransmitWindow` outside 1 to 7, a `MaxInfoField` outside 1 to 4090, or a non-positive `ClockSpeed`) throw `ArgumentOutOfRangeException` and an unsupported operating system throws `PlatformNotSupportedException`, both leaving the peer `Idle`. Otherwise `Start` throws `IOException` if the device cannot be opened, `ObjectDisposedException` if the peer is disposed meanwhile, and `OperationCanceledException` if canceled; those failures dispose the peer.
5. To form a connection, the caller calls `Connect(address, remoteAddress)`, which completes once the link is up. Unless `RetryInterval` is `null`, it sends a set asynchronous balanced mode (SABM) request immediately and again every `RetryInterval` until the remote peer answers. Independently of that, a request arriving from the remote peer is accepted and acknowledged, and also brings the link up. Equal addresses throw `ArgumentException` (the peer stays `Ready`), calling it when the peer is not `Ready` throws `InvalidOperationException`, and otherwise `IOException` (the device closes before the link is up), `ObjectDisposedException`, and `OperationCanceledException` dispose the peer.
6. `Send` transmits one information frame per call. Inbound information frames are passed to `Receiver` once each, in order and without gaps.
7. Disposing the peer (`Dispose` or `DisposeAsync`) sends a disconnect frame if still connected, stops receiving, and releases the device. A remote disconnect or a device failure ends the peer the same way, without disposal.

## Forming the link

HDLC asynchronous balanced mode has no client and server: both stations are equals and either may send the request, so the API has one `Connect` rather than separate connect and listen calls. Whether a side transmits requests is a setting, not a role. The usual choice is the default, where both sides send and whichever request lands first wins, so neither has to be started first. A `null` `RetryInterval` makes a side purely passive, for a remote that always initiates. Requests are repeated because the protocol implementation has no timers of its own and a request sent while the remote peer is not yet reading is otherwise lost. A side that is passive depends on the remote peer sending a request after this side is reading.

## Reliable delivery

While the peer is connected, data sent with `Send` arrives at the remote peer in order and without gaps. Each frame is numbered and kept until acknowledged, and is sent again when the remote peer rejects it or when `RetransmitInterval` passes without an acknowledgement. If `MaxRetransmissions` such timer driven resends pass with nothing acknowledged, the remote peer is considered gone and the peer becomes `Disconnected` (streams complete, waiting and later sends fail); without the limit a dead remote peer would leave the peer `Connected` indefinitely. At most `TransmitWindow` frames may be unacknowledged at once (up to 7, the most a modulo-8 HDLC sequence number space allows); a `Send` beyond that waits until an acknowledgement arrives, and fails with `IOException` if the peer disconnects while it waits or with `OperationCanceledException` if its token is canceled. A `Send` that completes means the frame was handed to the device, not that the remote peer has it. A `Send` whose write to the device fails throws `IOException` and takes the frame back, so the caller may repeat it without the data being delivered twice. A payload may be at most `MaxPayloadSize` bytes, which reflects `MaxInfoField` (up to 4090, since the drivers discard received frames over 4096 bytes and a frame also carries an address, a control field, and a frame check sequence); a larger `Send` throws `ArgumentOutOfRangeException` rather than being resent forever. A `MaxInfoField` smaller than the remote peer's own limit protects it from frames it would otherwise silently discard as too large.

A repeated connection request while connected (for instance a retry that crossed the answer) resets the link on both sides: sequence numbers restart at zero and any unacknowledged frames are renumbered and sent again, so nothing is lost, but the remote peer may then receive a frame it already had. Delivery is therefore exactly once and in order except across such a reset, where it is at least once.

Delivery to `Receiver` is hot: data that arrives while it is `null` is acknowledged and discarded, so set it before `Start`.

## Lifecycle

A peer is single use and only moves forward: `Idle`, then `Ready` (the device is open), then optionally `Connecting` and `Connected` (after `Connect`), then `Disconnected`. `Disconnected` is terminal and is reached by a remote disconnect, loss of the device, a failed or canceled start or establish, or disposal; a peer that has been started cannot be started again, and calling `Start` on it throws `InvalidOperationException`. A caller that wants to reconnect creates a new peer, which is why a container should register the peer as transient. Disposing a peer is still required after a remote disconnect to release the device.

## Observables

`StateChanged` is a standard `IObservable<T>` stream backed by a System.Reactive subject, so it composes with the rest of Rx. It completes once the peer is `Disconnected` and the data received before then has been delivered to `Receiver`, and subscribing to a peer that is already `Disconnected` completes immediately. It emits transitions from the moment of subscription; the current state is available from `State`. State changes and completion are delivered one at a time and in order, never concurrently and never while the peer holds a lock, so an observer may read `State` or call the peer from another thread. They are delivered synchronously, normally on the peer's receive thread, so an observer should hand work off rather than block. An observer that throws is unsubscribed, and does not affect other observers or the peer.

`Exceptions` is a second `IObservable<Exception>` for the exceptions that occur without breaking the connection, so the peer carries on after each: one thrown by the `Receiver` delegate or by a `StateChanged` observer (which is also unsubscribed), and a received frame too short to parse, which is dropped. Failures that do end the connection are not reported there; `StateChanged` shows them. Like `StateChanged` it is hot, so subscribe before `Start` or earlier exceptions are lost; it is delivered one at a time, in order, and never under a lock, together with the state changes, and completes with `StateChanged`. An exception thrown by an observer of `Exceptions` itself is ignored, since there is nowhere left to report it.

Received data is not a stream but a delegate, `Receiver` (`Action<IMemoryOwner<byte>>?`, `null` by default). The peer calls it once per frame, in order, each call returning before the next starts, from a task of its own, never while holding a lock and never from the thread that reads the device. Because of that the delegate may block, including on `Send` on the same peer, without stalling receiving or deadlocking: acknowledgements are still processed while it runs. It may also dispose the peer: that sends the disconnect and closes the device in the background once the peer's own threads have stopped, without waiting for the delegate. An exception from the delegate does not break the connection: it is reported on `Exceptions` and the next frame is delivered. The peer does not dispose the owner, since the delegate may already have handed it on. Data received before the peer became `Disconnected` is still delivered afterwards, unless the peer has been disposed. Frames are acknowledged as they arrive, so a delegate slower than the line lets received data queue up in memory.

## Payload data

The delegate is given an `IMemoryOwner<byte>` from the memory pool whose memory is exactly the frame's data, and owns it from then on: it disposes it as soon as it has finished with the data, returning the memory to the pool, and may keep it or hand it to another thread until then. The peer never disposes it after the call (an owner that is never disposed is only garbage collected), and the memory must not be modified or used after disposal. `Send(ReadOnlyMemory<byte>)` leaves ownership of its argument with the caller and copies it into pooled memory it keeps until the frame is acknowledged, while `Send(IMemoryOwner<byte>)` takes ownership and sends from that memory without copying, disposing it once the frame is acknowledged, or the send fails or the peer ends.

## Threading

`Send` may be called from any thread; writes are serialized so frames never interleave with each other or with the peer's automatic protocol responses.

## Monitoring and relaying

Monitoring is a facet of the peer, not a separate type. With `HdlcPeerOptions.EnableMonitor` set (it defaults to `false`, and then received frames are not even parsed for monitoring), every frame read from the device is parsed and pushed to the `Monitored` observable, whether or not a connection exists, in the order received. A peer that is only started therefore acts as a passive monitor: it forms no HDLC connection and, because the device's transmitter is only enabled when `Connect` or `Forward` first needs it, sends nothing on the line.

`Monitored` is `IObservable<HdlcFrame>`, one item per frame, decoded as far as its bytes allow. `HdlcFrame.Kind` is `HdlcFrameKind`, covering the nine frame kinds the peer handles internally, including the unnumbered and supervisory frames (SABM, DISC, UA, DM, FRMR, RR, RNR, REJ) two other stations use to manage their own connection, not just their information frames; a tenth kind, `Malformed`, covers a frame whose bytes could not be decoded, still reported (with `Raw` and `ErrorMessage`) rather than silently dropped. `HdlcFrame.Raw` holds the complete bytes as received (address, control, and data, without the frame check sequence); `Payload`, `SendSequence`, and `ReceiveSequence` are populated only for the kinds that carry them. `Monitored` reports the frames received; `Transmitted`, pushed under the same `EnableMonitor` switch, reports the frames the peer writes (requests, acknowledgements, information frames, resends, polls, responses, and anything sent with `Forward`) once they have reached the device, so the two together are the complete traffic of the link as this station sees it. Like `StateChanged`, the stream is hot, delivered one item at a time on the thread reading the device and never under a lock, and an observer that throws is reported on `Exceptions` without affecting the others.

`Forward(frame)` transmits a raw frame, exactly as `HdlcFrame.Raw` reports a received one, without involving the HDLC state machine. Two started peers on two devices, each forwarding what the other's `Monitored` reports, relay a link between two ports as if the relay were not there, while still seeing every frame. `Forward` is only allowed while the peer is `Ready`: once `Connect` has been called the peer's own protocol owns the transmitter, and mixing relayed frames into it would corrupt the connection's sequence numbers.

## UART peer

`IUartPeer` (created by `IUartPeerFactory` or `new UartPeer()`) uses the same devices as a plain asynchronous serial port: a raw byte stream with start and stop bits, no frames, addresses, acknowledgements or retransmission. It is a separate type because none of the HDLC concepts apply, and it is single use like the HDLC peer: construct, set `Receiver`, subscribe to `StateChanged` and `Exceptions`, then call `Start(portName, options)` once.

`UartPeerOptions` holds `BaudRate` (default 9600, any positive value), `DataBits` (5 to 8, default 8), `StopBits` (`One` or `Two`), `Parity` (`None`, `Even` or `Odd`) and `Loopback`. Both stations must agree on all four line settings, or bytes arrive garbled or are dropped; parity-error characters are discarded by the driver and the receiver accepts one or two stop bits regardless. Invalid values throw `ArgumentOutOfRangeException` from `Start` and leave the peer `Idle`; an unopenable device throws `IOException` and disposes the peer.

`Start` opens the port and enables the receiver, leaving the peer `Open`; the transmitter is enabled on the first `Send`. Received bytes are handed to `Receiver` as they arrive, in order, in chunks whose boundaries carry no meaning (a message may be split or joined). `Send` writes the bytes in order, serialized with other sends, and completes once the driver has accepted them. The peer states are `Idle`, `Open` and `Closed`; disposal, or a device failure, closes it and completes the observable streams. With data bits below 8 the unused high bits of received bytes are zero and sent bytes should not use them.
